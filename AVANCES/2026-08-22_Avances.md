## ✅ Cambio 1: Botón WhatsApp Dinámico en Errores (LISTO)

### Problema
Cuando el sistema getCID fallaba (error de Microsoft, OCR, token expirado, etc.), el cliente se quedaba sin saber qué hacer y no tenía forma rápida de pedir ayuda.

### Solución Implementada

#### Archivos modificados:
- `frontend/public/index.html` — Nueva sección de ayuda en el área de error
- `frontend/public/style.css` — Clase `.btn-wa-error` con animación pulse

#### Cómo funciona:
1. Cuando ocurre **cualquier error** (OCR, Microsoft, saldo, etc.), aparece automáticamente un panel verde con un botón de WhatsApp
2. El botón genera un enlace `wa.me/51907463313` con un **mensaje pre-llenado dinámico** que incluye:
   - 📧 El email o número de pedido que el cliente ingresó
   - 🔢 El IID completo (sea que lo escribió manualmente o lo detectó el OCR)
   - ⚠️ El código de error técnico (para diagnóstico rápido)
3. El cliente solo tiene que hacer clic → se abre WhatsApp → enviar
4. El botón tiene una **animación pulse verde** que llama la atención

## ✅ Cambio 2: Sistema Antireinicios Automático (LISTO)

### Problema
Los cortes de luz de ~30 minutos causaban que:
1. El token renovado (en memoria) se perdía al apagarse
2. Al encender, leía el `session_master.json` viejo con un token ya rotado
3. Microsoft rechazaba con `invalid_grant` → sistema muerto hasta intervención manual

### Solución Implementada (3 capas de protección)

#### Archivos modificados:
- `auth_http.py` — Escritura atómica + retry + refresh inmediato al arrancar
- `main.py` — Auto-refresh on-demand cuando falla un CID request

#### Capa 1: Escritura Atómica (`_save_session`)
- Cada vez que el daemon renueva tokens, los guarda **atómicamente** en `session_master.json`
- Usa patrón write-to-tmp + rename: escribe en `.tmp`, hace `fsync()` a disco, y luego `os.replace()`
- Si la luz se corta **durante** la escritura, el archivo original queda intacto

#### Capa 2: Retry con Backoff Exponencial (`refresh_access_token`)
- Ahora tiene 3 reintentos con esperas de 15s, 30s, 45s
- Crítico para después del corte de luz: la red puede tardar en estabilizarse
- Si el error es `invalid_grant` (permanente), no reintenta y marca como fallido

#### Capa 3: Refresh Inmediato al Arrancar (`start_daemon`)
- **ANTES:** El daemon esperaba 10-13 horas antes de renovar por primera vez
- **AHORA:** En cuanto arranca, renueva el token INMEDIATAMENTE
- Esto significa que después de un corte de luz, el sistema está operativo en ~5 segundos

#### Capa 4: Auto-Refresh On-Demand (`main.py` - `/check_pid`)
- Si un cliente pide un CID y Microsoft responde 401/403:
  1. Renueva el token automáticamente
  2. Reconstruye los headers con el nuevo token
  3. Reintenta la petición CID
  4. El cliente obtiene su CID sin saber que hubo un problema
- **ANTES:** El 401 mataba la petición y el cliente veía error
- **AHORA:** Se auto-heala y el cliente ni se entera
